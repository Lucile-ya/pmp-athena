# 3 敏捷项目管理

## 敏捷宣言

| 个体和互动 | > | 流程和工具 |
| 可工作的软件 | > | 详尽的文档 |
| 客户合作 | > | 合同谈判 |
| 响应变化 | > | 遵循计划 |

## Scrum 三大角色

| 角色 | 职责 | 不是做什么 |
|------|------|-----------|
| **产品负责人 (PO)** | 定义产品愿景，管理 Product Backlog，排序优先级 | 不管理团队日常 |
| **Scrum Master** | 清除障碍，推动流程，教练团队 | 不是经理，不是 PO |
| **开发团队** | 自组织交付，每个 Sprint 产出可工作增量 | 不接受外部干预排任务 |

## Scrum 五大事件

| 事件 | 时长 | 目的 |
|------|------|------|
| Sprint 规划 | ≤8h (1月Sprint) | 确定 Sprint 目标和 Sprint Backlog |
| 每日站会 | 15 分钟 | 同步进度：昨天、今天、障碍 |
| Sprint 评审 | ≤4h | 向干系人演示增量，获取反馈 |
| Sprint 回顾 | ≤3h | 团队反思改进（Start/Stop/Continue） |
| Sprint 本身 | 1-4周 | 产出可工作增量的时间盒 |

## 敏捷估算方法

| 方法 | 说明 |
|------|------|
| 故事点 (Story Points) | 相对大小估算，用斐波那契数列（1,2,3,5,8,13...） |
| 规划扑克 (Planning Poker) | 团队匿名投票，讨论差异，达成一致 |
| T恤尺寸 (T-Shirt Sizing) | 粗粒度分类：S/M/L/XL |
| 理想时间 (Ideal Time) | 不受干扰完成所需的实际时间 |

## 敏捷关键指标

| 指标 | 定义 |
|------|------|
| **速率 (Velocity)** | 团队每个 Sprint 完成的故事点总和 |
| **燃尽图 (Burndown Chart)** | 剩余工作量随时间递减 |
| **燃起图 (Burnup Chart)** | 已完成工作量随时间递增 |
| **累积流图 (CFD)** | WIP、完成、待办的累积分布 |
| **周期时间 (Cycle Time)** | 从开始做一个任务到完成任务的时间 |

## 敏捷十二原则速记

| # | 原则 |
|----|------|
| 1 | 最高优先级是尽早持续交付有价值的软件 |
| 2 | 拥抱需求变化，即使在开发后期 |
| 3 | 频繁交付可工作的软件（几周到几月） |
| 4 | 业务人员和开发者一起工作 |
| 5 | 围绕有动力的个体来构建项目 |
| 6 | 面对面沟通最有效 |
| 7 | 可工作的软件是进度的首要度量标准 |
| 8 | 保持可持续的节奏 |
| 9 | 持续关注技术卓越和良好设计 |
| 10 | 简洁（最大化未完成工作的艺术） |
| 11 | 最好的架构、需求和设计来自自组织团队 |
| 12 | 定期反思如何变得更高效 |

## 敏捷 vs 预测型选择

| 因素 | 偏向预测型 | 偏向敏捷型 |
|------|-----------|-----------|
| 需求 | 清晰、稳定 | 不确定、易变 |
| 技术 | 熟悉、成熟 | 新颖、快速变化 |
| 团队 | 有经验、分散 | 小规模、同地协作 |
| 客户参与 | 阶段性 | 持续参与 |
| 风险 | 低 | 高（需快速验证） |

## 关键敏捷术语

| 术语 | 定义 |
|------|------|
| MVP (Minimum Viable Product) | 最小可行产品 — 刚好够验证假设 |
| DoD (Definition of Done) | 完成定义 — 团队约定的完成标准 |
| WIP (Work In Progress) | 在制品 — 限制 WIP 是看板核心 |
| 用户故事 (User Story) | "作为<角色>，我想<功能>，以便<价值>" |
| Epics / Features / Stories | 从大到小的三层故事层级 |
| 信息发射源 | 燃尽图、看板、任务板（可视化信息） |
