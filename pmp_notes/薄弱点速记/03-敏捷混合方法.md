# 🟡 敏捷/混合方法 · 可背诵版

> **你的数据**：错误率 **50%**（70/141） · 错题本 64 题
> **总口诀**：**面对面 > 文档，团队决定 > PM 独断**

---

## 一、概念

**迭代增量**交付，拥抱变化，团队**自组织**。

### 敏捷宣言（左 > 右）

| 重视 | > | 相对次要 |
|------|---|----------|
| 个体和互动 | > | 流程和工具 |
| 可工作的软件 | > | 详尽的文档 |
| 客户合作 | > | 合同谈判 |
| 响应变化 | > | 遵循计划 |

> 不是不要计划/文档，是**优先级**不同。

---

## 二、三角色（最高频）

| 角色 | 做什么 | ❌ 不做什么 |
|------|--------|------------|
| **PO** | 定愿景、管 Backlog、**排优先级** | 不排团队日常任务 |
| **SM** | **清障碍**、教练团队 | 不是经理、**不定优先级** |
| **开发团队** | **自组织**交付增量 | 不接受外部强行派活 |

**口诀**：**PO 定 WHAT，团队定 HOW，SM 清路**

---

## 三、Scrum 五大事件

| 事件 | 时长 | 目的 |
|------|------|------|
| Sprint 规划 | ≤8h | Sprint 目标 + Sprint Backlog |
| 每日站会 | **15 分钟** | 昨天/今天/障碍 |
| Sprint 评审 Review | ≤4h | 演示增量、收反馈 |
| Sprint 回顾 Retro | ≤3h | 团队改进 |
| Sprint | 1–4 周 | 时间盒，产出增量 |

**口诀**：**规站评回 Sprint**

| 区分 | Review | Retro |
|------|--------|-------|
| 对象 | 干系人看增量 | 团队内部反思 |
| 输出 | 更新 Backlog | 改进行动项 |

---

## 四、Backlog 规则

```
新需求 → PO 写入 Product Backlog → 排优先级
         ↓
    默认不进当前 Sprint
         ↓
    除非 PO + 团队协商，且不影响 Sprint 目标
```

**口诀**：**新需求进 Backlog，别偷塞进 Sprint**

---

## 五、关键术语

| 术语 | 含义 |
|------|------|
| Product Backlog | 全产品待办，PO 维护 |
| Sprint Backlog | 本 Sprint 承诺的工作 |
| DoD | 团队约定的「什么叫完成」 |
| MVP | 最小可行产品 |
| Velocity | 每 Sprint 完成的故事点 |
| 信息发射源 | 燃尽图、看板、任务板 |

---

## 六、关键图表

| 图表 | 看什么 | 异常 |
|------|--------|------|
| 燃尽图 | 剩余工作递减 | 线平但活没干完 → **透明/文化问题** |
| 燃起图 | 已完成递增 | 同上 |

**口诀**：**燃尽失真查文化，别先怪工具**

---

## 七、敏捷 vs 预测型

| 偏向敏捷 | 偏向预测 |
|----------|----------|
| 需求不确定 | 需求清晰 |
| 技术新颖 | 技术成熟 |
| 小团队同地 | 大团队分散 |
| 客户持续参与 | 阶段性参与 |

---

## 八、十二原则精华（背 6 条）

1. 尽早持续交付有价值软件
2. 拥抱变化（即使后期）
3. **面对面沟通最有效**
4. 可工作软件是进度首要度量
5. 自组织团队出最好方案
6. 定期反思改进（Retro）

---

## 九、高频考点

1. PO/SM/团队职责边界
2. 新需求 → Backlog
3. 站会 15 分钟，团队回答，不是汇报 SM
4. Review vs Retro
5. 燃尽图失真 → 查透明/心理安全
6. 敏捷 ≠ 没计划；SM ≠ PM

---

## 十、易错陷阱

| ❌ 错 | ✅ 对 |
|------|------|
| SM 替团队排任务 | 团队自组织 |
| PM 独断决策 | 团队 + PO |
| Sprint 内静默加需求 | 进 Backlog 协商 |
| 站会变 status report | 15 分钟三问题 |
| 选冗长邮件沟通 | 交互式 > 推式 |
| 故事估不准就让 PO 给尺寸 | 计划扑克，团队多轮共同估 |
| 业务担心期望就先开工 | 先做发布计划/路线图对齐价值 |
| 技术细节不清就自己猜 | 请客户审查澄清当前 Sprint 功能 |
| 质量评审交给 SM | 开发团队 + PO 评审，SM 清障碍 |

## 十一、做题决策链

```
有 Sprint/Backlog/PO/SM/迭代？
  ├─ 谁定优先级 → PO
  ├─ 谁清障碍 → SM
  ├─ 谁决定怎么做 → 开发团队
  ├─ 新需求 → Backlog
  ├─ 沟通 → 面对面
  ├─ 故事估不准 → 计划扑克，团队估
  ├─ 开工前管期望 → 发布计划/路线图
  ├─ 技术细节不清 → 请客户澄清当前 Sprint
  └─ 燃尽图异常 → 查文化/透明
First → 沟通/协作，不选终局方案
```
