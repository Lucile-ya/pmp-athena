# 🟡 敏捷/混合方法 · 可背诵版

> **你的数据**：错误率 **51%**（78/154） · 错题本 72 题
> **总口诀**：**面对面 > 文档，团队决定 > PM 独断**

## 先搞懂（70 题 · 近期 21 · 持续弱点）

敏捷题你错，多半不是没背三角色，是**把预测型习惯（PM 做决定、有变化就改计划）套进 Sprint**。

### 1. 三个人，三件不能互相代劳的事

想象一家餐馆：

- **PO** = 点菜的人，决定先上哪道、哪道可以不上。这是业务价值，别人代劳就是越权。  
- **开发团队** = 后厨，决定怎么炒、一盘要多久。故事点由他们估（计划扑克），PO 给尺寸是外行指挥内行。  
- **SM** = 餐厅经理，后厨缺锅、隔壁挡道，他去清。他不点菜，也不下厨。

所以：优先级 → PO；障碍 → SM；怎么做、估多大 → 团队。你把障碍丢给 PO，等于让点菜的人去修煤气。

### 2. 当前 Sprint 是已经承诺的一锅菜

新需求可以点，但默认进菜单（Product Backlog）排队，不塞进正在炒的那一口。  
除非 PO 和团队一起决定：这道更重要，并且当前 Sprint 目标还能保。PM 自己加进去，破坏的是承诺和信任。

### 3. 供应商交不了货，不是 Backlog 问题（#87）

迭代里出现卖方，说明已经有采购协议。下一步是看合同允许你怎么救济，不是先改用户故事、不是先找下一家。敏捷改变的是**团队内部**怎么交付，不废除合同法。

### 4. 图好看但活没干完，先问人敢不敢说实话

燃尽图是信息发射源，它撒谎通常是文化问题：报喜不报忧、加班堆数字、不敢暴露障碍。换工具、强制加班，治的是表面。组织要「转敏捷」同理：只换模板没用，评估方式和领导行为不改，人还是不敢自组织。

混合题：规格已经钉死的部分用预测，还在变的部分用敏捷。看题干**此刻卡在哪一段**。

对照：[先搞懂再做题](./00-考前攻错决策卡.md)。

## 一、概念

**迭代增量**交付，拥抱变化，团队**自组织**。

### 敏捷宣言（左 > 右）

| 重视 | > | 相对次要 |
|------|---|----------|
| 个体和互动 | > | 流程和工具 |
| 可工作的软件 | > | 详尽的文档 |
| 客户合作 | > | 合同谈判 |
| 响应变化 | > | 遵循计划 |

> 不是不要计划/文档，是**优先级**不同。

---

## 二、三角色（最高频）

| 角色 | 做什么 | ❌ 不做什么 |
|------|--------|------------|
| **PO** | 定愿景、管 Backlog、**排优先级** | 不排团队日常任务 |
| **SM** | **清障碍**、教练团队 | 不是经理、**不定优先级** |
| **开发团队** | **自组织**交付增量 | 不接受外部强行派活 |

**口诀**：**PO 定 WHAT，团队定 HOW，SM 清路**

---

## 三、Scrum 五大事件

| 事件 | 时长 | 目的 |
|------|------|------|
| Sprint 规划 | ≤8h | Sprint 目标 + Sprint Backlog |
| 每日站会 | **15 分钟** | 昨天/今天/障碍 |
| Sprint 评审 Review | ≤4h | 演示增量、收反馈 |
| Sprint 回顾 Retro | ≤3h | 团队改进 |
| Sprint | 1–4 周 | 时间盒，产出增量 |

**口诀**：**规站评回 Sprint**

| 区分 | Review | Retro |
|------|--------|-------|
| 对象 | 干系人看增量 | 团队内部反思 |
| 输出 | 更新 Backlog | 改进行动项 |

---

## 四、Backlog 规则

```
新需求 → PO 写入 Product Backlog → 排优先级
         ↓
    默认不进当前 Sprint
         ↓
    除非 PO + 团队协商，且不影响 Sprint 目标
```

**口诀**：**新需求进 Backlog，别偷塞进 Sprint**

## 五、关键术语

| 术语 | 含义 |
|------|------|
| Product Backlog | 全产品待办，PO 维护 |
| Sprint Backlog | 本 Sprint 承诺的工作 |
| DoD | 团队约定的「什么叫完成」 |
| MVP | 最小可行产品 |
| Velocity | 每 Sprint 完成的故事点 |
| 信息发射源 | 燃尽图、看板、任务板 |

## 六、关键图表

| 图表 | 看什么 | 异常 |
|------|--------|------|
| 燃尽图 | 剩余工作递减 | 线平但活没干完 → **透明/文化问题** |

**口诀**：**燃尽失真查文化，别先怪工具**

---

## 七、敏捷 vs 预测型

| 偏向敏捷 | 偏向预测 |
|----------|----------|
| 需求不确定 | 需求清晰 |
| 技术新颖 | 技术成熟 |
| 小团队同地 | 大团队分散 |
| 客户持续参与 | 阶段性参与 |

---

## 八、十二原则精华（背 6 条）

1. 尽早持续交付有价值软件
2. 拥抱变化（即使后期）
3. **面对面沟通最有效**
4. 可工作软件是进度首要度量
5. 自组织团队出最好方案
6. 定期反思改进（Retro）

---

## 九、高频考点

1. PO/SM/团队职责边界
2. 新需求 → Backlog
3. 站会 15 分钟，团队回答，不是汇报 SM
4. Review vs Retro
5. 燃尽图失真 → 查透明/心理安全
6. 敏捷 ≠ 没计划；SM ≠ PM

## 十一、做题决策链

```
有 Sprint/Backlog/PO/SM/迭代？
  ├─ 谁定优先级 → PO
  ├─ 谁清障碍 → SM
  ├─ 谁决定怎么做 → 开发团队
  ├─ 新需求 → Backlog
  ├─ 沟通 → 面对面
  ├─ 故事估不准 → 计划扑克，团队估
  ├─ 开工前管期望 → 发布计划/路线图
  ├─ 技术细节不清 → 请客户澄清当前 Sprint
  ├─ 供应商交不了货 → 先审查采购协议（#87）
  └─ 燃尽图异常 → 查文化/透明
First → 沟通/协作，不选终局方案
```
