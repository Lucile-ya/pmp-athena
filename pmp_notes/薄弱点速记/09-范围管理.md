## 先搞懂（45 题 · 近期 16）

范围管理就一句话：**做且只做答应过的事。** 多做和少做都是错。


### 自动钉死（更新于 2026-11-20）

> 来自错题本高频口诀，跟「易错陷阱 / 背这句」同源，每天先扫这 5 条。

1. **怎么执行管控看项目管理计划** — 别只发目标声明
2. **验收争议先对齐验收标准** — 别未解决就放行付款
3. **敏捷范围定义先开PO协作研讨** — 别硬套预测型范围说明书
4. **经验教训要写进后续项目计划** — 别只存档不落地
5. **跨班次会议放在重叠时段** — 别固定只方便一班

### 1. 镀金和变更差在「谁提出来、走没走手续」

客户、拥护者、演示现场有人要加功能 → 这是变更请求，要评估对进度成本的影响，CCB 批了才能做。口头答应会变成范围蔓延。  
团队或 PM 自己觉得「还有余力，做漂亮一点」→ 镀金，即使不花客户的钱也不做。  
项目已经达到关闭标准（#84）→ 连变更都不必启动，释放资源走人。

### 2. WBS 回答「工作分解成哪些包」，不回答「谁负责」

两个团队工作重叠、角色不清，去翻 WBS 找不到人名。人名和职责在**资源管理计划 / RACI**。  
范围说明书解释「这个功能为什么存在」；WBS 解释「这个功能拆成哪些工作包」。成员不懂价值，查说明书，不是查 WBS。

### 3. 合格和验收是两步

QC：东西做得对不对（技术合格）。  
确认范围：干系人正式签字收货。  
先让人签字再检查，等于请客户验收半成品。永远先 QC，后确认范围。

## 一、概念

确保项目**做且只做**该做的事 — 定义和控制什么在内、什么在外。

## 三、范围基准

**范围基准 = WBS + WBS 词典 + 范围说明书**

| 概念 | 说明 |
|------|------|
| WBS | 可交付成果逐层分解为**工作包** |
| 工作包 | 最底层，可估算成本和时间 |
| 100% 规则 | WBS 涵盖项目 **100%** 工作 |
| 控制账户 | 管理控制点 |

**口诀**：**基准三件套：WBS + 词典 + 说明书**

---

## 四、需求 vs WBS

| | 需求 | WBS |
|--|------|-----|
| 回答 | 客户要什么 | 怎么做/怎么分解 |
| 工具 | 访谈、原型、焦点小组 | 分解 |

**口诀**：**需求是 WHAT，WBS 是 HOW 分解**

---

## 五、确认范围 vs 控制质量

| | 控制质量 QC | 确认范围 |
|--|-------------|----------|
| 做什么 | 检查是否**合格** | 干系人**正式验收** |
| 顺序 | **先** | **后** |

**口诀**：**先 QC 后确认**

---

## 六、范围蔓延 & 镀金

| 概念 | 说明 | 态度 |
|------|------|------|
| **范围蔓延** | 未控制的范围增加 | ❌ 禁止 |
| **镀金** Gold Plating | 主动加未要求的功能 | ❌ 不提倡 |
| 正确做法 | 记录 CR → 评估 → CCB 批准 | ✅ |

**口诀**：**加功能走变更，拒绝镀金蔓延**

---

## 七、高频考点

4. 客户加功能 → CR，不能口头接受
5. 需求跟踪矩阵的作用

## 八、易错陷阱

| ❌ 错 | ✅ 对 |
|------|------|
| （模拟考试1）目标怎么执行管控只发声明 | 用**项目管理计划**作集中信息源 |
| （模拟考试1）敏捷转型硬套范围说明书 | 先开 **PO+团队协作研讨**定 backlog/验收标准 |
| （模拟考试1）经验教训只存档 | 必须**写进后续项目计划**才算落地 |
| （模拟考试1）需求分歧硬开会推共识 | 先用 **RTM** 对齐需求与范围 |
| （模拟考试1）验收争议未解决就付款 | 先对齐**验收标准/合同质量**再签收 |
| 需求 = WBS | 需求是输入，WBS 是分解 |
| 先确认范围再 QC | 先 QC 后确认 |
| 口头接受范围变更 | 走 CR + CCB |
| PM 主动加功能（镀金） | 不提倡 |
| WBS 包含不属于项目的工作 | 100% 规则 |
| 职责不清就去翻 WBS | 查资源管理计划 / RACI |
| 不增客户成本却走变更扩范围 | 应急预算 + 内部 WBS + 管质量 |
| 演示后相关方要求加功能 | 走整体变更控制，不直接加 |

```

  → 先对齐验收标准/合同质量，再签收

  → 先开 PO+团队协作研讨定 backlog/验收（别硬套范围说明书）
需求分歧硬开会？
  → 先用 RTM 对齐需求与范围；RTM 要维护优先级
经验教训？
  → 必须写进后续项目计划，别只存档
范围调整压力大？
  → 先定优先级 + 环境分析，别怕伤士气照单全收

  → 确认范围（QC 之后）

  → 100% 规则，分解到工作包

不加客户成本的额外工作？
  → 应急储备 + 内部 WBS + 管质量，不扩范围
跨班次开会？
  → 放在重叠时段
```
