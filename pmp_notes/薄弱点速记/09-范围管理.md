## 先搞懂（45 题 · 近期 16）

范围管理就一句话：**做且只做答应过的事。** 多做和少做都是错。

### 1. 镀金和变更差在「谁提出来、走没走手续」

客户、拥护者、演示现场有人要加功能 → 这是变更请求，要评估对进度成本的影响，CCB 批了才能做。口头答应会变成范围蔓延。  
团队或 PM 自己觉得「还有余力，做漂亮一点」→ 镀金，即使不花客户的钱也不做。  
项目已经达到关闭标准（#84）→ 连变更都不必启动，释放资源走人。

### 2. WBS 回答「工作分解成哪些包」，不回答「谁负责」

两个团队工作重叠、角色不清，去翻 WBS 找不到人名。人名和职责在**资源管理计划 / RACI**。  
范围说明书解释「这个功能为什么存在」；WBS 解释「这个功能拆成哪些工作包」。成员不懂价值，查说明书，不是查 WBS。

### 3. 合格和验收是两步

QC：东西做得对不对（技术合格）。  
确认范围：干系人正式签字收货。  
先让人签字再检查，等于请客户验收半成品。永远先 QC，后确认范围。

## 三、范围基准

**范围基准 = WBS + WBS 词典 + 范围说明书**

| 概念 | 说明 |
|------|------|
| WBS | 可交付成果逐层分解为**工作包** |
| 工作包 | 最底层，可估算成本和时间 |
| 100% 规则 | WBS 涵盖项目 **100%** 工作 |
| 控制账户 | 管理控制点 |

**口诀**：**基准三件套：WBS + 词典 + 说明书**

## 四、需求 vs WBS

| | 需求 | WBS |
|--|------|-----|
| 回答 | 客户要什么 | 怎么做/怎么分解 |
| 工具 | 访谈、原型、焦点小组 | 分解 |

**口诀**：**需求是 WHAT，WBS 是 HOW 分解**

---

## 五、确认范围 vs 控制质量

| | 控制质量 QC | 确认范围 |
|--|-------------|----------|
| 做什么 | 检查是否**合格** | 干系人**正式验收** |
| 顺序 | **先** | **后** |

**口诀**：**先 QC 后确认**

---

## 六、范围蔓延 & 镀金

| 概念 | 说明 | 态度 |
|------|------|------|
| **范围蔓延** | 未控制的范围增加 | ❌ 禁止 |
| **镀金** Gold Plating | 主动加未要求的功能 | ❌ 不提倡 |
| 正确做法 | 记录 CR → 评估 → CCB 批准 | ✅ |

**口诀**：**加功能走变更，拒绝镀金蔓延**

2. WBS 100% 规则
3. 确认范围 vs 控制质量顺序
4. 客户加功能 → CR，不能口头接受
5. 需求跟踪矩阵的作用

---

## 八、易错陷阱

| ❌ 错 | ✅ 对 |
|------|------|
| 需求 = WBS | 需求是输入，WBS 是分解 |
| 先确认范围再 QC | 先 QC 后确认 |
| 口头接受范围变更 | 走 CR + CCB |
| PM 主动加功能（镀金） | 不提倡 |
| WBS 包含不属于项目的工作 | 100% 规则 |
| 职责不清就去翻 WBS | 查资源管理计划 / RACI |
| 不增客户成本却走变更扩范围 | 应急预算 + 内部 WBS + 管质量 |
| 演示后相关方要求加功能 | 走整体变更控制，不直接加 |

## 九、做题决策链

```
客户要加功能？
  → 记录 CR → 评估 → CCB（不是口头接受）
问范围基准？
  → WBS + 词典 + 说明书
验收/Sign-off？
  → 确认范围（QC 之后）
WBS 分解？
  → 100% 规则，分解到工作包
职责/角色不清？
  → 资源管理计划 / RACI，不是 WBS
不加客户成本的额外工作？
  → 应急储备 + 内部 WBS + 管质量，不扩范围
```
