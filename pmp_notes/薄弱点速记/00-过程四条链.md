## 进场先过这四句

看见题干里的信号，先在心里说完左句，再看选项。

| 看见 | 背这句 | 别踩 |

| 改基准、变更、合并、收尾 | 先评估影响，走变更控制，干系人先对齐 | 自称不影响就直接改；硬并流程；未对齐验收就收尾 |
| 进度落后、要压缩、估算偏大 | 先分析再行动；重叠是快速跟进；SV=EV−PV | 先全员赶工；拍脑袋砍工期；用完工百分比冒充 SV |
| 范围外工作、验收争议、需求分歧 | 范围外先变更；验收先对标准；需求用跟踪矩阵维护优先级 | 直接改 WBS；未解决就放行；照单全收 |
| 缺陷、不合格、凭感觉说合格 | 先对照质量标准做控制质量，再找根因改过程 | 只修这一件；先交付后补；凭经验放行 |

## 整合

**1. 谁有权改整体**

**总口诀：变更先评估，CCB 后实施。**

### 概念

整合管理是**识别、定义、组合、统一和协调**各项目管理过程。项目经理是整合者。考的是谁有权改整体，以及改之前必须先知道会炸到哪。

| 概念 | 定义 |
|------|------|
| 项目章程 | 发起人签发，正式授权项目经理动用资源。项目经理参与制定，不签发 |
| 章程里有什么 | 目的、目标、成功标准、高层级需求、里程碑、预算、项目经理任命 |
| 整体变更控制 | 书面变更请求 → 评估对范围/进度/成本/质量的影响 → CCB → 批准后才改基准和实施 |
| 项目经理能批什么 | 只批不影响基准的小改动。影响基准的交给 CCB |
| 问题 | 已经发生。记入问题日志 |
| 风险 | 可能发生。记入风险登记册 |
| 工作绩效数据 | 原始测量，执行阶段产生 |
| 工作绩效信息 | 拿数据和基准对比，监控阶段 |
| 工作绩效报告 | 汇总后供决策 |
| 变更日志 | 变更记在这里 |
| 配置管理 | 管产品的版本和可追溯。变更不要写进配置管理计划 |

### 先搞懂

**变更是一条不能跳的链。** 有人要改范围、进度、成本、合同，你还不知道对三条基准各影响多少。立刻实施、口头答应、直接改计划，都是在未知影响时动手。顺序是：写成变更请求 → 评估影响 → CCB（或有权的人）批准 → 才改基准和实施。PM 只能自行批不影响基准的小改动。任何变更要书面，口头须补书面。跳过评估直接交 CCB，同样错。

**已经发生和可能发生不是同一本账。** 还没砸下来 → 风险登记册，选规避 / 转移 / 减轻 / 接受。已经砸下来（数据丢了、设备拿不到了）→ 问题日志，先处理、先找根因。经验教训会要开，但不是「首先」。

**做完了就要关。** 关闭标准一旦满足，项目存在的理由消失。余钱余时间退回组织。加功能、加一轮没要求的检查，都是镀金。

**章程是发起人发给你的许可证。** 授权的是「你可以动用资源去干这件事」，签发人是发起人，不是 PM。它对齐的是 PM 和赞助组织的期望，不是客户和分包商（那些用合同、用干系人参与）。启动阶段事业环境因素改了范围，先动章程，不要先改详细计划。提交章程前可以回顾组织的经验教训。

组织抵制变革时，先让人理解为什么变（培训 / 沟通），硬推会把整合做失败。变革已成定局，先通知受影响的用户并请求合作。监管方是一票否决相关方，他们的要求要进范围、改 WBS，不当成普通变更打发。成员不懂功能价值，查范围说明书解释好处和原因。

### 七大过程

| 过程 | 过程组 | 核心输出 |
|------|--------|----------|
| 制定项目章程 | 启动 | 项目章程、假设日志 |
| 制定项目管理计划 | 规划 | 项目管理计划 |
| 指导与管理项目工作 | 执行 | 可交付成果、变更请求 |
| 管理项目知识 | 执行 | 经验教训登记册 |
| 监控项目工作 | 监控 | 工作绩效报告 |
| 实施整体变更控制 | 监控 | 批准的变更请求 |
| 结束项目或阶段 | 收尾 | 最终报告、经验教训 |

工作绩效三层：数据是原始测量（执行），信息是和基准对比（监控），报告是汇总给决策（监控）。经验教训全周期都记，收尾再总结。分阶段迁移时，每一阶段都做知识转移，不要拖到最后只写一篇教训。

## 进度

**2. 关键路径零浮动**

**总口诀：关键路径零浮动，赶工加钱，并行有险。**

### 概念

进度管理是在资源约束下安排活动顺序和时间，按时交付。关键路径上没有可以浪费的空闲。非关键路径有浮动，晚一点不一定拖总工期。缩短非关键活动，总工期不动。

| 概念 | 定义 |
|------|------|
| 关键路径 | 最长路径 = 项目最短完成时间。上面的活动总浮动 = 0。可以同时有多条 |
| 总浮动 | 活动推迟多久仍不影响总工期 |
| 赶工 | 加资源、加班。顺序不变，成本上升 |
| 快速跟进 | 把先后做的事搭接。顺序变了，返工风险上升 |
| 有钱没时间 | 赶工 |
| 不能加成本还要提前 | 快速跟进 |
| 类比估算 | 早期、快、粗 |
| 参数估算 | 有历史公式 |
| 三点估算 | 对付不确定性 |
| 自下而上 | 最准，也最慢。估算明显偏大时用它重估 |
| SV / SPI | SV = EV − PV，SPI = EV / PV。小于 0 或小于 1 表示落后 |
| 资源平衡 | 解决资源超负荷。可以改进度，关键路径可能变长 |
| 资源平滑 | 只在浮动时间内调整，总工期不变 |
| 提前且不能加钱 | 快速跟进。资源平衡不负责这件事，赶工要加钱 |

### 先搞懂

**赶工和快速跟进。** 赶工 = 同一件事加人、加班，花钱，顺序不变，风险主要是累和贵。快速跟进 = 本来先后做的事搭着做，顺序变了，返工风险上升。活动已经重叠，那就是快速跟进，不是发 MVP，也不是加人。有钱没时间 → 赶工。不能加成本、又要提前 → 快速跟进。没有可以重叠的活动，就做资源优化或赶工，不要硬并行。PMP 在「可以加资源」时经常选赶工。

**落后不要直接全员加班。** 先问为什么落后（资源被抽走、依赖、范围暗增）。SPI < 1 只说明落后，不说明该赶工还是该改依赖。「可能影响进度」是风险，先记入风险登记册，再评估、再应对。发起人要砍两个月，先做赶工和快速跟进的权衡，当场承诺就是错。浮动时间以内的延误，用结构化沟通把真实状态说清，不要让私下传言把项目说成已经落后。

**关键路径。** 最长路径 = 项目最短完成时间。关键路径上总浮动 = 0。可以同时有多条关键路径。

**估算。** 类比早、粗。参数靠历史公式。三点对付不确定性。自下而上最准，估算明显偏大时用 WBS 自下而上重估，不要拍脑袋砍数字。

**和挣值。** SV = EV − PV，SPI = EV / PV。问进度偏差，报 SV，不要用完工百分比冒充。只给了 EV 和 PV、没问成本，SV < 0 就是进度落后，去做进度压缩，不要先动成本基准。

**敏捷和项目之间。** 站会不追绝对工期，用相对估算、故事点；进展用已交付的价值来证明，不靠发起人口头说正常。燃尽图、报告失真，先查透明和信任，不先换工具。多个有联系的项目进度打架，交给项目集经理，不是当成 PMO 的日常支持。争议很大、开放讨论会失控，用名义小组技术。

| 题干 | 背这句 | 别踩 |

### 决策链

```

  ├─ 当场要你承诺砍掉几个月 → 先做权衡分析
  ├─ 不能加成本 → 快速跟进
  ├─ 可以加资源 → 赶工
  ├─ 没有可重叠的活动 → 资源优化或赶工

给网络图 → 最长路径 = 最短工期

估算偏大 → WBS 自下而上
SPI < 1 → 先找根因，再选压缩手段
```

## 范围

**3. 做且只做答应过的事**

**总口诀：范围基准三件套，先 QC 后确认。**

### 概念

范围管理确保项目做且只做该做的事：什么在内，什么在外。多做和少做都是错。

| 概念 | 定义 |
|------|------|
| 范围基准 | WBS + WBS 词典 + 项目范围说明书 |
| WBS | 可交付成果逐层分解到工作包。工作包是最底层，可以估算成本和时间 |
| 100% 规则 | WBS 涵盖全部项目工作，不多也不少 |
| 需求 | 客户要什么（WHAT）。工具是访谈、原型、焦点小组 |
| WBS 和需求的差别 | 需求是输入，WBS 是怎么分解（HOW）。WBS 不管谁负责 |
| 谁负责 | 资源管理计划 / RACI |
| 控制质量 | 检查是否合格。在前 |
| 确认范围 | 干系人正式验收。在 QC 之后 |
| 范围蔓延 | 未走控制的范围增加 |
| 镀金 | 团队或项目经理主动加没人要求的功能。即使不另外收费也不做 |
| 需求跟踪矩阵 | 把需求和可交付成果、优先级对上，并且要维护 |

### 先搞懂

**镀金和变更差在谁提出来、走没走手续。** 客户、拥护者、演示现场有人要加功能 → 变更请求，评估对进度成本的影响，CCB 批了才能做。口头答应会变成范围蔓延。团队或 PM 自己觉得「还有余力，做漂亮一点」→ 镀金，即使不花客户的钱也不做。项目已经达到关闭标准 → 连变更都不必启动，释放资源走人。不加客户成本的额外工作，用应急储备、内部 WBS 和管理质量消化，不把范围扩出去。

**WBS 回答工作拆成哪些包，不回答谁负责。** 两个团队工作重叠、角色不清，翻 WBS 找不到人名。人名和职责在资源管理计划 / RACI。范围说明书解释「这个功能为什么存在」；WBS 解释「拆成哪些工作包」。成员不懂价值，查说明书。

**合格和验收是两步。** 控制质量：东西做得对不对。确认范围：干系人正式签字。先让人签字再检查，等于请客户验收半成品。顺序永远是先 QC，后确认范围。确认范围还要和干系人协商批准，不只是自己验证「符合要求」。

**需求是客户要什么，WBS 是怎么分解。** 需求跟踪矩阵要把需求和范围对上，并且维护优先级，不是建完表就放着。需求分歧先用跟踪矩阵对齐，不要硬开共识会压过去。有人要求调范围，先定优先级，再做环境分析。高优先级需求可以多方协作、快速交付。

**怎么执行、怎么管控，看项目管理计划**，计划是集中的信息源。只发一页目标声明，团队不知道怎么管。经验教训必须写进后续项目的计划，存档不算落地。跨班次开会，放在两班重叠的时段。已经清楚的范围用预测，复杂、还在变的部分用敏捷。

### 六大过程

| 过程 | 过程组 | 核心输出 |
|------|--------|----------|
| 规划范围管理 | 规划 | 范围管理计划 |
| 收集需求 | 规划 | 需求文件、需求跟踪矩阵 |
| 定义范围 | 规划 | 项目范围说明书 |
| 创建 WBS | 规划 | WBS、范围基准 |
| 确认范围 | 监控 | 验收的可交付成果 |
| 控制范围 | 监控 | 变更请求 |

**范围基准 = WBS + WBS 词典 + 范围说明书。** WBS 把可交付成果逐层分解到工作包。工作包是最底层，可以估算成本和时间。100% 规则：WBS 涵盖项目全部工作，不多也不少。

## 质量

**4. 看这一件，还是看那套办法**

**总口诀：QA 管过程，QC 管结果。**

### 概念

质量管理把组织的质量政策用到项目上，让可交付物满足要求。管理层对质量负最终责任。题几乎都在问：你现在是在看这一件东西，还是在看生产它的那套办法。

| 概念 | 定义 |
|------|------|
| 规划质量管理 | 把标准定下来。输出质量管理计划、质量测量指标 |
| 管理质量 QA | 查过程是否按计划走。工具是审计、过程分析。执行阶段 |
| 控制质量 QC | 查这一件交出来合不合格。工具是检查、统计抽样。监控阶段 |
| 确认范围 | 干系人验收。必须排在 QC 合格之后 |
| 预防成本 | 培训、把流程设计对。最便宜，优先投 |
| 评估成本 | 检查、测试。缺陷已经可能存在 |
| 内部失败 | 交付前返工 |
| 外部失败 | 保修、退货、诉讼。最贵 |
| 鱼骨图 | 找根本原因 |
| 帕累托图 | 少数原因造成多数问题 |
| 控制图 | 过程是否受控 |
| 散点图 | 一个变量是否影响另一个 |

### 先搞懂

用医院比喻，忘掉缩写。

- **QC 控制质量**：化验这杯血合不合格。对象是可交付物。题干出现检测、缺陷数量、是否达标 → QC。
- **QA 管理质量**：化验室流程乱不乱、审计有没有按计划做。对象是过程。出现质量审计、没遵守计划、改进流程 → QA。
- **确认范围**：家属在化验单上签字。必须先合格，才能请人验收。

检测出比平常更多的错误，测的是产品，那是 QC。测完发现过程有病，再去做 QA。敏捷里质量出了问题，开回顾，团队自己找根因；Scrum Master 清障碍，不替团队审质量。

**修这一件，防止不了下一件。** 重复缺陷：先用鱼骨图找根因，再改过程。只返工当前产品，下一件还会坏。问「如何避免再发」，选预防（培训、改设计、改流程）。多检查几遍是评估成本，发生在缺陷之后。

**质量问题已经出现，先当问题记账。** 文档引用了不相关产品、现场交货不合格：已经发生，先进问题日志，必要时看合同里的质量条款。先改沟通计划，是跳到了后面的格子。移交前要证明合格，对照质量标准和度量。不合格走控制质量流程，不要先交付后修补。管理层对质量负最终责任。

### 三大过程

| 过程 | 过程组 | 关注 | 核心输出 |
|------|--------|------|----------|
| 规划质量管理 | 规划 | 定标准 | 质量管理计划、质量测量指标 |
| 管理质量 QA | 执行 | 过程 | 质量报告、审计 |
| 控制质量 QC | 监控 | 结果 | 核实的可交付成果 |

| | QA | QC |
|--|----|----|
| 关注 | 过程是否合规 | 结果是否达标 |
| 工具 | 质量审计、过程分析 | 检查、统计抽样 |
| 谁 | 全员 | 质量控制人员 |

### 质量成本

预防（培训、把流程设计对）最便宜，也是优先投资。然后是评估（检查、测试），内部失败（返工），外部失败（保修、诉讼）最贵。问「如何避免再发」→ 预防。

| 工具 | 用来做什么 |
|------|------------|
| 鱼骨图 | 找根本原因 |
| 帕累托图 | 少数原因造成多数问题 |
| 控制图 | 过程是否受控 |
| 散点图 | 一个变量是否影响另一个 |
| 流程图 | 把过程步骤画出来 |

### 你的错题口诀

| 题干 | 背这句 | 别踩 |
|------|--------|------|
| 重复缺陷、质量问题 | 先根因，再改过程 | 只修当前这一件 |
| 「感觉合格了」 | 对照质量标准和度量 | 凭经验放行 |
| 可交付物不合格 | 走控制质量流程 | 先交付后修补 |
| 检测出很多错误 | 查结果 = QC | 直接选 QA |
| 问过程、审计、改进流程 | QA | 选成 QC |
| 质量反馈机制失灵 | 和团队一起审查质量过程 | 只改这一批产品 |

### 决策链

```

检查 / 测试 / 这件东西合格吗 → QC

```

## 成本

**5. 先算 EV，再分两笔储备**

**总口诀：挣值先算 EV，应急在基准，管理要变更。**

### 概念

成本管理是在批准的预算内完成项目，顺序是规划 → 估算 → 制定预算 → 控制成本。机构「项目财务管理」曾经 7/30。公式要认，但错更多出在第一步看什么。

| 概念 | 定义 |
|------|------|
| 生命周期成本 | 建设成本 + 交给客户之后的运行成本 |
| 沉没成本 | 已经花掉、收不回。决定继续还是停止时不算它 |
| 机会成本 | 选了这个、放弃另一个所失去的收益 |
| 收益递减 | 人加一倍，工期不会缩成一半 |
| 折旧 | 资产随时间掉值。直线折旧对税更不利 |
| 价值工程 | 用在新产品上，降成本、提质量。老产品用价值分析 |
| 成本从哪来 | 资源、采购、风险、质量 |
| 估算精度 | 早期粗略量级大约 −25%～+75%；后期确定性大约 −5%～+10% |
| PV | 计划价值：按计划此刻应完成多少 |
| EV | 挣值：按预算价，实际干完了多少。做题先算它 |
| AC | 实际成本：已经花出去的钱 |
| BAC | 完工预算：总预算 |
| CV / CPI | CV = EV − AC，CPI = EV / AC。小于 0 或小于 1 表示超支 |
| SV / SPI | SV = EV − PV，SPI = EV / PV。小于 0 或小于 1 表示落后 |
| TCPI | (BAC − EV) / (BAC − AC)。大于 1：剩下的钱要比原来花得更省 |
| 应急储备 | 已知风险。在成本基准里，项目经理可以动 |
| 管理储备 | 未知的未知。不在成本基准里，要用先走变更 |
| 成本基准 | 工作包成本 + 应急储备。不含管理储备 |
| 项目预算 | 成本基准 + 管理储备 |
| 控制账户 | 把范围、预算、进度绑在一个节点上盯 |
| 固定总价 FFP | 成本超支风险主要在卖方 |

### 先搞懂

**余钱不是用来再做好一点的。** 答应的东西已经交付，关闭标准已经满足。再加功能、再加一轮没要求的质量检查，都是镀金。剩下的钱和时间属于组织，确认关闭后释放。只有变更被批准才能加。拥护者「希望」不等于批准。

**不能只看花了多少钱。** PV 是计划此刻该完成的价值。AC 是已经掏出去的现金。EV 是按预算计价、你真正干完了多少。花了预算的 80%，可能只干完 50%，那是超支。题目给数字，先算 EV，再用 EV 减 AC 看成本、用 EV 减 PV 看进度。CPI、SPI 是这两个比较的除法：小于 1 就是超支或落后。图里只有 AC 和 PV、没有 EV，无法判断预算有没有问题，不要猜「预算水平有问题」。

**两笔储备不要混。** 应急储备对付已知风险（零件可能涨价），放进成本基准，项目经理可以动。管理储备对付未知的未知，不在基准里，要用等于改基准，走变更，通常由发起人批。项目预算 = 成本基准 + 管理储备。成本基准 = 工作包成本 + 应急储备。登记册里已经写明的风险，动应急储备。「预算储备」太笼统。问储备够不够，用以往绩效做预测和完工估算，不要只报账上还剩多少。

**三个过程不要串台。**

| 过程 | 你在干什么 | 典型工具 |
|------|------------|----------|
| 估算成本 | 算出大概要花多少 | 类比、参数、三点、自下而上 |
| 制定预算 | 汇总成基准，放进储备 | 储备分析、成本汇总 |
| 控制成本 | 盯偏差，管变更是否有益 | 挣值、趋势、项目管理信息系统 |

控制成本不是再估一遍，也不是建基准。它盯的是会改成本基准的因素，并确认变更有益。日常控制用项目管理信息系统，不要只口头压预算。

**估算方法看手里有什么。** 类比：有类似项目，快但不准。参数：有公式和历史数据。三点 (O+4M+P)/6：估一个数，对付不确定性。自下而上：工作包逐个估再加总，最准也最慢；没有任何可参考数据时，只能自下而上。时间只有几小时，用类比或粗略量级，不要硬上自下而上。发起人要看「预算」、问编制预算用什么，优先想储备分析，不要一看到「准」就选自下而上。发起人嫌贵、手里有历史数据，用类似项目证明合理性，不要换一套估算法糊弄。

三点、储备分析、蒙特卡洛不要混。三点是估一个数。价格会晃、已知风险要留钱，选储备分析；选项里的「应急预算」多半是干扰项。蒙特卡洛是大量抽样，画出整个项目可能结果的分布，不是关键路径，也不是资源平衡。

**控制账户**把范围、预算、进度绑在一个节点上盯。考「在哪把三件事对齐」→ 控制账户。

**资金到位有时间限制**，先调整进度，让支出节奏匹配到账，不要先改成本基准。预算被砍，先查融资和资金措施，再谈范围。材料短缺，用多元化供应，不要干等一家。迭代里功能抢资源，按优先级做成本分析，不要平均撒。外部环境影响用 PESTEL 审视，不要只更新干系人登记册。不想动用应急储备，就主动预防威胁。质量成本和可持续有压力，先分析再提变更。

**合同和机会。** 尽可能把成本超支风险转给卖方 → 固定总价（FFP）。总价加经济价格调整只调物价；成本加成、成本加激励是成本补偿，买方风险更大。客户拒绝预算内、计划里写明的必要外聘：先评估不做的后果，再当面解释。发现提前交付能降成本、客户又盯着下一个里程碑：这是机会，走变更管理和客户谈，不要直接加人赶工。CV 为负、SV 为正，多半在拿钱换时间。CV 为正、SV 为负，看着省钱、进度落后。TCPI = (BAC−EV)/(BAC−AC)，大于 1 表示剩下的钱要花得比原来更省，很难完成。

### 挣值

| 指标 | 公式 | 大于 0 或大于 1 | 小于 0 或小于 1 |
|------|------|-----------------|-----------------|
| CV | EV − AC | 节约 | 超支 |
| SV | EV − PV | 提前 | 落后 |
| CPI | EV / AC | 节约 | 超支 |
| SPI | EV / PV | 提前 | 落后 |
| TCPI | (BAC−EV)/(BAC−AC) | 剩余很难按原预算完成 | 还有余地 |

完工估算：偏差会持续，EAC = AC + (BAC−EV)/CPI。剩余按原预算做，EAC = AC + (BAC−EV)。要重估，EAC = AC + 新的自下而上估算。

减法看偏差（CV、SV），除法看指数（CPI、SPI）。EV 比 PV 大就超前，EV 比 AC 大就省钱。

| 把超支风险转给卖方 | 固定总价 | 成本补偿，或只调物价的总价 |
| 客户拒绝必要外聘 | 先评估后果，再沟通 | 偷偷用内部资源硬顶 |
| 提前完工能降成本 | 走变更，跟客户谈 | 直接加人赶工 |
| 关闭标准已满足还有余钱 | 释放资源 | 拿去镀金 |
| 没有任何历史数据 | 自下而上 | 类比或三点 |

### 决策链

```
给数字 → 先算 EV
  ├─ 问成本 → CV、CPI
  ├─ 问进度 → SV、SPI
  ├─ 问还能不能按预算完工 → TCPI
  └─ 问最后花多少 → 看偏差会不会持续，再选 EAC
图里只有 AC + PV → 缺 EV，无法判断
已知风险、价格波动 → 应急储备 / 储备分析
未知的未知 → 管理储备 + 变更
资金受限 → 调进度
预算被砍 → 先查融资
转超支风险给卖方 → 固定总价
关闭标准已满还有余钱 → 释放，不镀金
```

### 闪卡

| 问 | 答 |
|----|-----|
| 做题第一步？ | 先算 EV |
| CPI < 1？ | 超支 |
| SPI < 1？ | 进度落后 |
| 成本基准含管理储备吗？ | 不含 |
| 应急储备谁能动？ | 项目经理，在基准内 |
| 管理储备怎么用？ | 走变更 |
| 项目预算？ | 成本基准 + 管理储备 |
| 沉没成本参与继续还是停止？ | 不参与 |
| 价值工程用在哪？ | 新产品；老产品是价值分析 |
| 价格波动选什么技术？ | 储备分析 |

<a id="风险"></a>

## 风险

**6. 先对上策略，发生了就执行**

**总口诀：威胁用规避转移减轻接受，机会用开拓提高分享接受。超出权限才上报。**

错题本 12 道。今天又错：风险已经发生，却想再开会重找缓解。

### 概念

还没发生的写风险登记册，选应对。已经发生的写问题日志，或直接执行当初写好的应对。

| 概念 | 定义 |
|------|------|
| 规避 | 消除威胁，或让目标碰不到它 |
| 转移 | 把影响和责任交给第三方：保险、外包、固定总价 |
| 减轻 | 把概率或影响降下来：备份供应商、合同条款、违约金 |
| 接受 | 不主动出手。主动接受会留应急储备；被动接受就是等它发生 |
| 上报 | 威胁或机会超出项目经理权限，交给上层。权限内的不要上报 |
| 开拓 | 确保机会发生。把最强的资源派上去 |
| 提高 | 只提高机会的概率或好处，并不保证它发生 |
| 分享 | 把机会分给更能抓住它的第三方 |
| 权变 | 风险发生后临时想的办法。事先写好的叫应急计划 |
| 次生风险 | 应对本身带来的新风险，要再登记 |

高概率、高影响的威胁，默认想减轻或规避，不要直接选接受。

### 你的错题口诀

| 题干 | 背这句 | 别踩 |
|------|--------|------|
| 事先记过的风险已经发生（谈判开始了、威胁落地了） | 执行当初写好的应对 | 再开会重新找缓解 |
| 组件坏了、数据已经泄露 | 当问题：先分析原因和影响 | 只写进风险登记册 |
| 知道会有影响，细节还不明 | 先更新风险登记册 | 直接改计划或换人 |
| 高概率、高影响的威胁 | 减轻：条款、违约金、备份 | 默认接受，或先想权变 |
| 多选应对 | 把关键策略选全再执行 | 漏掉那条真正对上的 |
| 还没变成问题 | 按风险监控，不要升级 | 拿新闻去通知干系人 |
| 要把机会做成必然（最强资源、提前完工） | 开拓 | 选成提高 |
| 外部供应商带来威胁 | 先审合同条款，再写应对 | 先换供应商 |

### 决策链

```
已经发生 → 执行既定应对，或记入问题日志
可能发生、细节不清 → 更新风险登记册 → 再评估 → 再应对
问策略名字
  ├─ 威胁：规避 / 转移 / 减轻 / 接受 / 上报
  └─ 机会：开拓 / 提高 / 分享 / 接受 / 上报
确保机会发生 → 开拓
只是提高概率 → 提高
超出项目经理权限 → 上报
```

### 闪卡

| 问 | 答 |
|----|-----|
| 确保机会发生？ | 开拓 |
| 提高概率但不保证？ | 提高 |
| 保险、固定总价转走威胁？ | 转移 |
| 降低概率或影响？ | 减轻 |
| 风险已经发生？ | 执行既定应对 |
| 什么时候上报？ | 超出项目经理权限 |

## 采购

**7. 先看合同里写了什么**

**总口诀：争议和绩效先对照合同，变更走变更控制，了解表现做采购审计。**

错题本 6 道。过程卷会把采购绑进变更和风险里考。

### 概念

| 概念 | 定义 |
|------|------|
| 采购审计 | 把采购全过程审查一遍，总结经验教训。问「了解这些合同表现得怎样」选审计 |
| 档案记录 | 只负责留存。不管总结，也不等于了解表现 |
| 控制采购 | 用合同里的度量看卖方绩效 |
| 合同变更 | 书面变更请求，先评估影响和风险。批准前不实施 |
| 固定总价 | 超支风险主要在卖方 |
| 成本补偿 | 超支风险主要在买方 |
| 工料合同 | 双方分摊，范围说不清时常见 |

### 你的错题口诀

| 题干 | 背这句 | 别踩 |
|------|--------|------|
| 要了解多种合同的表现 | 做采购审计 | 只整理档案 |
| 规格对不上（样品长度、图纸各说各话） | 先看合同里约定的规格 | 上报采购部，或先加一道返工 |
| 卖方要改工作说明书 | 先评估影响，做风险分析 | 先改流程，或先换卖方 |
| 采购绩效差 | 先对照合同度量 | 先换卖方 |
| 验收或争议 | 按合同和标准谈 | 项目经理单方让步 |
| 合同条款要改 | 走变更控制 | 私下改 |
| 供应商交接、知识会断 | 一起回顾，双向分享所需知识 | 只让对方留一份档案 |
| 外部供应商的威胁 | 先审合同条款再规划应对 | 先换供应商 |
