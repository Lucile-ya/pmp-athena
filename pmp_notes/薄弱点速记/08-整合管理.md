## 先搞懂（57 题 · 近期 24）

整合不是「把各领域拼起来」这么抽象。它考的是：**谁有权改整体，以及改之前你必须先知道会炸到哪。**


### 自动钉死（更新于 2026-11-25）

> 来自错题本高频口诀，跟「易错陷阱 / 背这句」同源，每天先扫这 5 条。

1. **合并变革先引导干系人看价值** — 别先硬并流程组织
2. **ESG愿景对齐定期找发起人** — 别团队自行猜战略

4. **远程双团队共用单一文档库** — 别多套登记册失控
5. **次要里程碑顺序差先分析影响** — 别立刻改基准

### 1. 变更是一条不能跳的链

有人要改范围、进度、成本、合同——你还不知道对三条基准各影响多少。  
立刻实施、口头答应、直接改计划，都是在未知影响时动手。  
正确顺序：写成变更请求 → 评估影响 → CCB（或有权的人）批准 → 才改基准和实施。  
PM 只能自行批**不影响基准**的小改动。

### 2. 「已经发生」和「可能发生」不是同一本账

还没砸下来 → 风险登记册，选规避/转移/减轻/接受。  
已经砸下来（数据丢了、设备拿不到了）→ 问题日志，先处理、先找根因。  
你的 #83 选经验教训，就是把收尾动作拿到处理问题之前。教训会要开，但不是「首先」。

### 3. 做完了就要关，不要因为还有钱就继续

关闭标准一旦满足，项目存在的理由消失。余钱余时间退回组织。加功能、加一轮没要求的检查，都是镀金。详见 #84。

### 4. 章程是发起人发给你的许可证

章程授权的是「你可以动用资源去干这件事」，签发人是发起人，不是 PM。  
它对齐的是 **PM 和赞助组织** 的期望，不是客户和分包商（那些用合同、用干系人参与）。  
组织抵制变革时，先让人理解为什么变（培训/沟通），硬推只会把整合做失败。监管方是一票否决相关方，他们的要求通常要进范围、改 WBS，而不是当成普通 CR 打发。

## 四、整体变更控制（最高频）

```
变更请求提交
  ↓
评估对范围/进度/成本/质量的影响  ← 第一步！
  ↓
提交 CCB 审批
  ↓
批准后更新基准 + 实施
  ↓
记录变更日志
```

### 关键规则

| 规则 | 说明 |
|------|------|
| 任何变更需**书面**请求 | 口头需补书面 |
| **CCB 批准前不得实施** | 先评估再执行 |
| PM **不能**自行批准影响基准的变更 | 可批准不涉及基准的小变更 |
| 口头变更 ≠ 已批准 | 必须走流程 |

**口诀**：**记录→评估→CCB→批准→实施**

## 六、高频考点

1. 变更流程：评估 → CCB → 批准 → 实施
2. 章程签发人 = 发起人

| （模拟考试1）合并/组织变革先硬并流程 | 先**引导干系人过变革**，盯住价值 |
| （模拟考试1）远程双团队多套文档库 | **单一文档登记册** + 变更控制 |
| （模拟考试1）裁剪方法照搬上家公司 | 先摸清本组织**文化/不确定性容忍度** |
| （模拟考试1）未对齐验收/DoD就收尾 | 先明确并与干系人**共享验收标准** |
| （模拟考试1）持续改进只靠口号 | 建**高频数据反馈**文化 |

## 八、做题决策链

```
新变更/范围增加/客户加功能？
  → 记录 CR → 评估影响 → CCB → 批准后实施（别口头答应）
问章程？
  → 发起人签发；提交前可回顾组织经验教训
问 PM 第一步？
  → 分析/记录/评估（P1），不是执行
Risk vs Issue？
  → 已发生=Issue（问题日志），可能发生=Risk
合并/组织变革？
  → 先引导干系人看价值，别先硬并流程
远程双团队文档乱？
  → 单一文档登记册 + 变更控制
裁剪方法？
  → 先摸清本组织文化/不确定性容忍度，别照搬上家
收尾前验收/DoD？
  → 先明确并与干系人共享，别未对齐就收尾
持续改进？
  → 高频数据反馈文化，别只贴海报
ESG/战略愿景？
  → 定期与发起人对齐，别团队自行猜
次要里程碑顺序差？
  → 先分析影响，别立刻改基准
组织抵制变革 → 先培训/沟通目的，不硬推
变革已成定局 → 先通知受影响用户并请求合作
一票否决相关方 → 纳入范围，更新 WBS
```
