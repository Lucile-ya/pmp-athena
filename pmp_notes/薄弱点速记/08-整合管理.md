## 先搞懂（57 题 · 近期 24）

整合不是「把各领域拼起来」这么抽象。它考的是：**谁有权改整体，以及改之前你必须先知道会炸到哪。**

### 1. 变更是一条不能跳的链

有人要改范围、进度、成本、合同——你还不知道对三条基准各影响多少。  
立刻实施、口头答应、直接改计划，都是在未知影响时动手。  
正确顺序：写成变更请求 → 评估影响 → CCB（或有权的人）批准 → 才改基准和实施。  
PM 只能自行批**不影响基准**的小改动。

### 2. 「已经发生」和「可能发生」不是同一本账

还没砸下来 → 风险登记册，选规避/转移/减轻/接受。  
已经砸下来（数据丢了、设备拿不到了）→ 问题日志，先处理、先找根因。  
你的 #83 选经验教训，就是把收尾动作拿到处理问题之前。教训会要开，但不是「首先」。

### 3. 做完了就要关，不要因为还有钱就继续

关闭标准一旦满足，项目存在的理由消失。余钱余时间退回组织。加功能、加一轮没要求的检查，都是镀金。详见 #84。

### 4. 章程是发起人发给你的许可证

章程授权的是「你可以动用资源去干这件事」，签发人是发起人，不是 PM。  
它对齐的是 **PM 和赞助组织** 的期望，不是客户和分包商（那些用合同、用干系人参与）。  
组织抵制变革时，先让人理解为什么变（培训/沟通），硬推只会把整合做失败。监管方是一票否决相关方，他们的要求通常要进范围、改 WBS，而不是当成普通 CR 打发。

对照：[先搞懂再做题](./00-考前攻错决策卡.md)。

## 四、整体变更控制（最高频）

```
变更请求提交
  ↓
评估对范围/进度/成本/质量的影响  ← 第一步！
  ↓
提交 CCB 审批
  ↓
批准后更新基准 + 实施
  ↓
记录变更日志
```

### 关键规则

| 规则 | 说明 |
|------|------|
| 任何变更需**书面**请求 | 口头需补书面 |
| **CCB 批准前不得实施** | 先评估再执行 |
| PM **不能**自行批准影响基准的变更 | 可批准不涉及基准的小变更 |
| 口头变更 ≠ 已批准 | 必须走流程 |

**口诀**：**记录→评估→CCB→批准→实施**

## 六、高频考点

1. 变更流程：评估 → CCB → 批准 → 实施
2. 章程签发人 = 发起人
3. 经验教训**全周期**记录，收尾总结
4. 问题日志 vs 风险登记册（已发生 vs 可能发生）
5. PM 是整合者，统管各知识领域变更

## 七、易错陷阱

| ❌ 错 | ✅ 对 |
|------|------|
| 收到变更立刻执行 | 先评估 + CCB |
| PM 批准基准变更 | CCB 批准 |
| 口头接受范围变更 | 书面 CR |
| 跳过评估直接提交 CCB | 先分析影响 |
| 已发生问题写风险登记册 | 问题日志 |
| 组织抵制变革就硬推 | 先培训，让干系人理解变更目的 |
| 变革已定还先评估方案 | 先通知用户并请求合作 |
| 一票否决相关方只走 CR | 纳入范围、更新 WBS |
| 成员不懂功能价值 | 查范围说明书解释好处与原因 |
| 已授权要高绩效团队先定标准 | 先选有技能/潜力的成员 |

## 八、做题决策链

```
新变更/范围增加/客户加功能？
  → 记录 CR → 评估影响 → CCB → 批准后实施
问章程？
  → 发起人签发，正式授权 PM
问 PM 第一步？
  → 分析/记录/评估（P1），不是执行
Risk vs Issue？
  → 已发生=Issue，可能发生=Risk
组织抵制变革 → 先培训/沟通目的，不硬推
变革已成定局 → 先通知受影响用户并请求合作
一票否决相关方 → 纳入范围，更新 WBS
```
